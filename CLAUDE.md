# Decision log

## 2026-09-14: menutile, the public release of a private menu bar renderer
- What this is: the generic SwiftBar/xbar-dialect renderer that runs a status script from inside its own signed .app bundle with its own LaunchAgent, extracted from a private menu bar host and sanitized for release. The private host keeps its fleet-specific plugins, rosters and installers; this repo carries only the renderer, a generic per-tile installer, the shared bundle builder, parser tests and the README's notification-identity explanation.
- Why a bundle (the ruling this repo exists to document): macOS presents banners and attributes process names only to real LaunchServices-registered .app bundles. An Info.plist beside the interpreter or the framework Python's own Python.app identity both yield an API that accepts notifications while the system files them without presenting them and without any System Settings entry. The objective test is UNUserNotificationCenter authorizationStatus, not a clean return.
- Pattern: bundle = copy of the uv-managed static CPython + Info.plist + optional icns + ad-hoc signature; stdlib and site-packages via PYTHONHOME and PYTHONPATH in the LaunchAgent; the renderer scrubs both from children. Known failure: a removed or moved PYTHONHOME exits 78 before Python runs a line, silently; the README tells the reader to read `launchctl list` and re-run install.sh.
- Differences from the private original, on purpose: the bash= allowlist is the script's own directory plus system bin dirs plus --allow-root (the original hard-codes the owner's roots); defaults for bundle id and label are com.menutile.<slug>; the installer takes one tile per invocation with a name-collision check; no fleet plugins.
- scripts/make_bundle.sh is a verbatim copy of the one in the switchdeck repo (public), which owns it; keep them byte-identical (cmp) when either moves.
- Forced refresh (2026-10-25, ported from the private original's 2026-10-04 change): `refresh=true force=true` runs the script once with `MENUTILE_FORCE=1` in the child env only; `poll()` check-and-sets under the lock, a forced click during a run is queued and re-polled forced when it ends, timer ticks during a run are dropped. The variable name is this repo's own (the original's carries the private host's name). Tests: tests/test_refresh.py (6 cases at the port, 10 after review); 5 of the first 6 fail against the pre-port renderer.
- Review round 1 (2026-10-25, 8 findings). Fixed: `_child_env()` drops an inherited MENUTILE_FORCE, so only a manual click forces a run; a queued forced refresh now runs from `apply_pending` after the previous result is shown, so it can never overwrite that result or its one-shot notify lines; a click during a forced run is not queued again (a double-click costs one run); a failed worker start resets the running flags instead of freezing polling. tests/test_refresh.py has 10 cases, including the idle forced path through a real thread and an inherited host value. Recorded, not changed: a row with both `refresh=true` and `bash=` runs only the refresh (unchanged from the first release; documenting or changing that is its own decision); CI runs gitleaks only, because the tests need macOS with rumps; the workflow matches the author's other public repos (unfiltered push plus pull_request, actions on major tags).
- CI: .github/workflows/gitleaks.yml, the same file the author's other public repos run (push, pull request, weekly). Since 2026-10-31 a root .gitleaks.toml also applies; see that entry.
- Naming: "menutile" was checked on 2026-09-14 against GitHub (no repos of that name), the process list, launchctl and /Applications before the folder was created.

## 2026-10-31: forced refresh, the gap before apply_pending (ported review fixes)
- Three fixes ported from the private original's 2026-10-30 review, one commit each, each with a tests/test_refresh.py case that fails on its parent: a render that raises still runs the queued click (ac5cab0, the poll sits in a finally); a timer tick is dropped while a queued click is due (2722362, so a plain run cannot overwrite the unapplied result); a forced click in that gap clears the due mark (26ee408, so one intent costs one forced run).
- Review round 1 (2026-10-31, 7 findings). Fixed in cc574f7: a click in that gap still started a run at once, so a fast script could overwrite the unshown result and its one-shot notify lines. poll now waits while a result or a queued click is pending: a timer tick is dropped, and a forced click becomes the forced run apply_pending starts after the result is shown. That replaces 26ee408's "clear the due mark". Recorded, not changed: a render that raises still propagates into the rumps timer, as before the port (catching it is its own change); the finding that the finally block hides the render error is wrong, because Python chains both exceptions.
- Review round 2 (2026-10-31, 8 findings). Added a test that runs the real poll through click, apply_pending and worker start. Recorded, not changed: a due click is still lost when the worker thread fails to start from apply_pending (no re-arm on a failed start, the private original's decision; a re-arm would retry and log every second); a forced click in the microseconds between a forced run's result and its finally is covered by that run (the double-click rule); handing results to the main thread directly instead of the one-second apply timer, and merging _force_queued into _force_due, are refactors for their own change.
- Review round 3 (2026-10-31, 7 findings, the last round). Fixed in d48483e: cc574f7 dropped a timer tick or plain click in the wait. Both timers start together with whole-second periods, so for a script whose run time is up to a second shorter than the interval every other tick landed there and the tile refreshed at half the rate; a "Retry now" click there did nothing. A plain poll in the wait is now postponed to apply_pending, and a forced click in the same wait still wins (one run). Recorded, not changed: the render-raise path and the two refactors (as in rounds 1 and 2); two near-copy wait tests (style); the Thread patch reaches the stdlib module, but only inside each with block of a single-threaded test. d48483e came after the third round, so no review round has read it; its test fails on its parent. tests/test_refresh.py has 17 cases; the suite has 31.
- Unchanged by decision: a click during a forced run is not queued again; the next timer tick covers a late second click.
- scripts/make_bundle.sh was not touched; still byte-identical (cmp) to the switchdeck copy.
