# Decision log

## 2026-09-14: menutile, the public release of a private menu bar renderer
- What this is: the generic SwiftBar/xbar-dialect renderer that runs a status script from inside its own signed .app bundle with its own LaunchAgent, extracted from a private menu bar host and sanitized for release. The private host keeps its fleet-specific plugins, rosters and installers; this repo carries only the renderer, a generic per-tile installer, the shared bundle builder, parser tests and the README's notification-identity explanation.
- Why a bundle (the ruling this repo exists to document): macOS presents banners and attributes process names only to real LaunchServices-registered .app bundles. An Info.plist beside the interpreter or the framework Python's own Python.app identity both yield an API that accepts notifications while the system files them without presenting them and without any System Settings entry. The objective test is UNUserNotificationCenter authorizationStatus, not a clean return.
- Pattern: bundle = copy of the uv-managed static CPython + Info.plist + optional icns + ad-hoc signature; stdlib and site-packages via PYTHONHOME and PYTHONPATH in the LaunchAgent; the renderer scrubs both from children. Known failure: a removed or moved PYTHONHOME exits 78 before Python runs a line, silently; the README tells the reader to read `launchctl list` and re-run install.sh.
- Differences from the private original, on purpose: the bash= allowlist is the script's own directory plus system bin dirs plus --allow-root (the original hard-codes the owner's roots); defaults for bundle id and label are com.menutile.<slug>; the installer takes one tile per invocation with a name-collision check; no fleet plugins.
- scripts/make_bundle.sh is a verbatim copy of the one in the switchdeck repo (public), which owns it; keep them byte-identical (cmp) when either moves.
- Forced refresh (2026-10-25, ported from the private original's 2026-10-04 change): `refresh=true force=true` runs the script once with `MENUTILE_FORCE=1` in the child env only; `poll()` check-and-sets under the lock, a forced click during a run is queued and re-polled forced when it ends, timer ticks during a run are dropped. The variable name is this repo's own (the original's carries the private host's name). Tests: tests/test_refresh.py (6 cases at the port, 10 after review); 5 of the first 6 fail against the pre-port renderer.
- Review round 1 (2026-10-25, 8 findings). Fixed: `_child_env()` drops an inherited MENUTILE_FORCE, so only a manual click forces a run; a queued forced refresh now runs from `apply_pending` after the previous result is shown, so it can never overwrite that result or its one-shot notify lines; a click during a forced run is not queued again (a double-click costs one run); a failed worker start resets the running flags instead of freezing polling. tests/test_refresh.py has 10 cases, including the idle forced path through a real thread and an inherited host value. Recorded, not changed: a row with both `refresh=true` and `bash=` runs only the refresh (unchanged from the first release; documenting or changing that is its own decision); CI runs gitleaks only, because the tests need macOS with rumps; the workflow matches the author's other public repos (unfiltered push plus pull_request, actions on major tags).
- CI: .github/workflows/gitleaks.yml, the same file the author's other public repos run (push, pull request, weekly). Since 2026-10-31 a root .gitleaks.toml also applies; see that entry.
- Naming: "menutile" was checked on 2026-09-14 against GitHub (no repos of that name), the process list, launchctl and /Applications before the folder was created.

## 2026-10-31: forced refresh, the gap before apply_pending (ported review fixes)
- Three fixes ported from the private original's 2026-10-30 review, one commit each, each with a tests/test_refresh.py case that fails on its parent: a render that raises still runs the queued click (ac5cab0, the poll sits in a finally); a timer tick is dropped while a queued click is due (2722362, so a plain run cannot overwrite the unapplied result); a forced click in that gap clears the due mark (26ee408, so one intent costs one forced run).
- Review round 1 (2026-10-31, 7 findings). Fixed in cc574f7: a click in that gap still started a run at once, so a fast script could overwrite the unshown result and its one-shot notify lines. poll now waits while a result or a queued click is pending: a timer tick is dropped, and a forced click becomes the forced run apply_pending starts after the result is shown. That replaces 26ee408's "clear the due mark". Recorded, not changed: a render that raises still propagates into the rumps timer, as before the port (catching it is its own change); the finding that the finally block hides the render error is wrong, because Python chains both exceptions.
- Review round 2 (2026-10-31, 8 findings). Added a test that runs the real poll through click, apply_pending and worker start. Recorded, not changed: a due click is still lost when the worker thread fails to start from apply_pending (no re-arm on a failed start, the private original's decision; a re-arm would retry and log every second); a forced click in the microseconds between a forced run's result and its finally is covered by that run (the double-click rule); handing results to the main thread directly instead of the one-second apply timer, and merging _force_queued into _force_due, are refactors for their own change.
- Review round 3 (2026-10-31, 7 findings, the last round). Fixed in d48483e: cc574f7 dropped a timer tick or plain click in the wait. Both timers start together with whole-second periods, so for a script whose run time is up to a second shorter than the interval every other tick landed there and the tile refreshed at half the rate; a "Retry now" click there did nothing. A plain poll in the wait is now postponed to apply_pending, and a forced click in the same wait still wins (one run). Recorded, not changed: the render-raise path and the two refactors (as in rounds 1 and 2); two near-copy wait tests (style); the Thread patch reaches the stdlib module, but only inside each with block of a single-threaded test. d48483e came after the third round, so no review round has read it; its test fails on its parent. tests/test_refresh.py has 17 cases; the suite has 31.
- Unchanged by decision: a click during a forced run is not queued again; the next timer tick covers a late second click.
- scripts/make_bundle.sh was not touched; still byte-identical (cmp) to the switchdeck copy.

## 2026-11-17: click actions on an exact --allow-action list; split on newline only
- Source: the author's fleet security audit of 2026-11-16, finding MFMT1 (Medium). The allow list was folders, not commands: the script's own folder, /usr/bin, /usr/local/bin, /opt/homebrew/bin and any --allow-root, so a row that outside text slipped into the output could run env, sh, osascript or python3 with any arguments; a bare name was checked as <working dir>/<name> but run from PATH; and splitlines() also split on \r, \v, \f, \x1c to \x1e, U+0085, U+2028 and U+2029, so outside text holding one could start a row of its own. The private original got the same fix the same day.
- SUPERSEDES the 2026-09-14 line "the bash= allowlist is the script's own directory plus system bin dirs plus --allow-root".
- Owner decisions 2026-11-17: (1) exact commands, `--allow-action "/abs/program arg ..."` (repeatable, shell quoting), not `--allow-exe` with free arguments; a row runs only when its bash= path is a listed program path or the file it resolves to (narrowed after /security-review; at first any path resolving to the same file) and its param1..paramN (no gap) equal that entry's arguments exactly; the path as listed runs (review round 1; it was the resolved path at first); checked at menu build and again at the click; the default list is empty. (2) Shells and interpreters stay banned even when listed (env, sh, bash, zsh, dash, ksh, csh, tcsh, fish, osascript, osacompile, perl*, ruby*, node, nodejs, deno, bun, python*, php*, lua*, tclsh*, wish*, swift; by the file name given and the file it resolves to, case-insensitive), although with every argument pinned the ban adds little: it mainly makes users put a command in a script file. (3) `--allow-root` stays accepted by menutile.py and is ignored with one log line, so an agent installed before this change starts with its click rows off instead of exiting in a launchd loop; install.sh refuses it with a message, because a person runs the installer. (4) The README says, in the same commit, that this breaks existing click rows, gives one `--allow-action` example, and says rows that build a URL on the fly can no longer be clickable.
- SPLIT: ported from the private original as is. parse_output splits on "\n" only (one trailing \r before the \n is always dropped, since review round 2; a `---` separator matches after stripping only spaces and tabs). parse_line turns a line holding a control character (tab and ESC excepted, since review round 2), U+2028/U+2029 or a bidi control into plain text with no parameters, each such character shown as U+FFFD. The source writes these characters as escapes, never raw.
- WHAT BROKE: on the author's Mac nothing (no tile installed, no venv, no agent, nothing else calls menutile.py). For anyone else, every bash= row until they re-run install.sh with --allow-action lines (README "Upgrading").
- TESTS: tests/test_actions.py, 28 cases after the review rounds. Red-first proof against the parent (git archive copy, final test file of round 1 plus the security fix, 22 cases): 18 failed, 4 passed by design (normal output, CRLF, tab, the Terminal row quoting); each review fix's tests failed on the code before that fix. subprocess.Popen is a recorder in every clicking test, so even the old code runs nothing. The old roots test in tests/test_parse.py is removed with action_roots; the test file keeps no fallback for the old API. Suite 32 to 59, run with another local venv that has rumps 0.4.0 on Python 3.14, because ~/.menutile-venv does not exist on the author's Mac.
- Review round 1 (2026-11-17, /code-review medium, 9 findings; each checked here). Fixed, each with a test that failed on the round's first code: (1) the click ran the resolved path, so a program that acts on its own name changed behaviour (/usr/bin/view is vim): the path as listed runs; (2) a refused row was logged on every refresh, so an older tile wrote one line per row per poll: logged once per process (capped at 200 distinct rows); (3) install.sh took any --allow-action and the install reported success: it runs the renderer's own check after the venv step and fails, naming the reason (tested under /bin/bash 3.2 with set -u); (4) a row with a gap in its param numbers matched with fewer arguments than it shows: refused (also param0, param01); (5) launchers that run another command passed the interpreter ban: arch, xargs, nohup, nice, time, timeout, sudo, doas, su, login, script, caffeinate, xcrun, find and awk added (best effort, the pinned arguments are the gate; /usr/bin/open stays allowed, the README example uses it); (6) U+061C was not a suspect character: added; (7) the module docstring printed a real line break for "\\n": escaped. Recorded, not changed: (8) every refresh resolves every entry for every row (cheap, and resolving each time is what catches a file swapped after start); (9) install.sh refuses --allow-root while menutile.py ignores it: the owner's decision (3), because a person runs the installer and an agent restarts in a loop. /security-review (2026-11-17): no finding at confidence 8 or above. Its one note below that (about 3 of 10, also true of the old code): building the menu ran realpath on any path a row named, and on a Mac with the /net automount that could make it look up a host named in outside text (TO VERIFY whether /net is active on current macOS). Fixed anyway, test first: a row must name a listed program path or the file that path resolves to, so only listed paths are ever resolved; a row path with .. or another spelling of a listed file is now refused. Seen while fixing: three test lines had been written with raw separator and bidi characters; now escapes.
- Review round 2 (2026-11-17, /code-review medium, 10 findings, no blocking bug). Fixed, test first: (1) install.sh passed a mistyped program path: it now also checks each listed program is an executable file; (2) entries no row can match (an argument holding " | " or a control character) installed silently: refused; (3) mixed line endings (CRLF lines, then a plain echo) broke every "---\r" separator: one trailing \r before \n is always dropped, a \r inside a line still makes it plain text (a trailing \r cannot start a row); (4) an ANSI colour code (ESC) emptied a row's params: ESC is exempt, it ends no line and is not a bidi control; (6) more command runners in the ban (command, expect, launchctl, sandbox-exec, ssh, tmux, screen, pwsh, emacs, vi, vim, view, ex, nvim and relatives; README says best effort); (9) the tests' fallback for the removed API: deleted. Recorded, not changed: (5) terminal= is not pinned by the entry, so injected text can open a listed command in Terminal instead of the background (same program and arguments; pinning it needs entry syntax, a later decision); (7) zero-width characters (U+200B to U+200D, U+2060, U+FEFF) are not suspect: an injected row can already copy a real label without them, and U+200D is part of many emoji, which would lose their row's params; (8) a refused row is logged once per process even when it is refused again for another reason; (10) the install check runs after the venv build, because menutile.py imports rumps at the top (a module split is its own change).
- Review round 3, the last (2026-11-17, /code-review medium, 7 findings). Fixed, test first: (1) THE SPLIT FIX DID NOT REACH THE RUNNING APP: _worker read the script with subprocess.run(text=True), whose universal newlines turn a lone \r (and \r\n) into \n before parse_output, so "News: x\rRun | bash=<listed>" still made a clickable row; the earlier tests called parse_output with hand-made strings and could not see it. _worker now reads bytes and decodes UTF-8 with replacement (also ends the old "a multibyte title can fail the decode" failure; README note updated); (2) new RealOutput tests run a real script through _worker (lone \r, CRLF, a non-UTF-8 byte), the \r one red on the code before; (3) more runners in the best-effort ban (shortcuts, automator, java, Rscript, julia, irb, uv, uvx, npx, npm, pipx, make, git; /usr/bin/open stays); (4) install.sh and the renderer share one runnable() check; (5) the configure_actions docstring says why a missing program is kept there and refused by install.sh; (6) the interpreter check per row runs once, on the resolved file; (7) the title filter strips only spaces and tabs, like the separator check. These fixes came after the third and last review round; no review round has read them. A second /security-review on the final diff (after round 3) found no finding at confidence 8 or above; below that it noted that rumps keys menu items by title, so an injected row with a real row's label can replace that row (it can only put a listed command, or none, under that label), and that a fish login shell reads backslashes in single quotes differently from shlex.quote (listed arguments are trusted). The private original reads its scripts the same way (text=True), so its newline-only split has the same gap in the running app: recorded for its own session, not changed here (other repo). Suite 59.
- scripts/make_bundle.sh was not touched; still byte-identical (cmp) to the switchdeck copy.
